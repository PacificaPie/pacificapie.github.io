Collaborative Roadmap — Cloud Sync & a Conversational Update Loop 协作式路线图 —— 云端实时同步与对话驱动更新

Personal · Collaboration Shipped Agents · Skills
two-person tool, one repo  ·  led the front-end rework, cloud persistence, and the update-loop skill 双人工具、同一仓库  ·  主导前端改版、云端持久化与更新链路技能

The problem

A two-person roadmap and gantt tool, one repo — but my collaborator built through an AI code-generation platform that kept regenerating the UI and quietly overwriting hand edits. And with local-only storage, two devices could never really share state.

My call

I treated it as an engineering-discipline problem, not a styling one: centralize what the platform AI keeps clobbering, move shared state to a real-time cloud, and turn "update it by talking to it" into a portable skill.

What shipped

  • Overwrite-resistant theming — the platform AI kept resetting colors, so I pulled the whole palette into a single theme.js: restore in one place, and the design is back.
  • Real-time cloud sync — Supabase (PostgREST + realtime subscriptions); data modeled as one row per person, a single JSON blob, so two writers never conflict; least privilege — anonymous role can read/write but not delete rows.
  • A conversational update loop — a self-contained Node CLI (native fetch, no dependencies) that turns "natural language → change the data → live refresh" into a globally callable skill.

The discipline

Two writers on one repo needed a rule, not heroics: fetch / rebase before pushing, merge rather than force. When the platform AI reshaped the structure wholesale, I stopped fighting the conflict and instead re-aligned to their latest, then re-applied the theme.

What iterating taught me

Collaborating with an AI code-generation platform is really a state-management problem: separate what it regenerates from what must persist, and give every change a disciplined path in.

The shift that stuck: from "human edits the file" to "an agent edits by natural language" — the moment updating a product becomes a pipeline, not a chore.

问题

双人协作的路线图 / 甘特工具，同一个仓库 —— 但另一位开发者通过 AI 代码生成平台施工， 平台会反复重新生成 UI、悄悄覆盖手工改动。而纯本地存储，意味着两台设备根本无法真正共享状态。

我的判断

我把它当工程纪律问题，而非配色问题：把平台 AI 反复覆盖的东西集中化、 把共享状态搬到实时云端、并把“用自然语言改它”封装成可移植的技能。

交付

  • 抗覆盖的主题化 —— 平台 AI 反复把配色改回去，于是我把全站配色抽到单一 theme.js：一处恢复，设计即复原。
  • 云端实时同步 —— Supabase（PostgREST + 实时订阅）；数据建模为 “每人一行、单个 JSON blob”，两人各写各行、天然无写冲突；最小权限 —— 匿名角色可读写但无删行权。
  • 对话驱动更新链路 —— 自包含 Node CLI（原生 fetch、零依赖）， 把“自然语言 → 改数据 → 实时刷新”封装成可全局调用的技能。

纪律

两人写同一个仓库，靠的是规则不是蛮力：先 fetch / rebase 再推、用 merge 不强推。 当平台 AI 把结构整体大改，我不再硬解冲突，而是先对齐对方最新结构、再重套主题。

认知迭代

与 AI 代码生成平台协作，本质是个状态管理问题：把它反复生成的、和必须持久的分开， 再给每次改动一条有纪律的入口。

真正留下的转变：从“人改文件”到“让 agent 用自然语言改” —— 更新一个产品从此是一条链路，而不是一件苦差。
