ResourceLoop — Matching Campaign Themes with the Right Products ResourceLoop —— 为活动主题匹配合适的商品

Internship · Meituan美团实习 Internal内部项目 Applications应用层
internship project (internal)  ·  Workflow, data model, recommendation rules, and acceptance criteria · frontend and backend implementation with AI 实习项目（内部）  ·  工作流、数据模型、推荐规则与验收标准 · 与 AI 协作完成前后端实现

A concert, match, or festival can suggest a campaign theme. Making that theme useful takes another set of decisions: which products fit, whether the price and stock work, and whether customers can reasonably get from the event to the product location. ResourceLoop brings those decisions into one workflow, upstream of an internal advertising-page builder.

Where this system fits

ResourceLoop selects activity themes, retrieves and screens product supply, and gives people a place to review and adjust the recommendations. Its handoff is a structured set of selected themes, suitable products, and resource suggestions. A separate team owns the downstream ad-building agent, which uses the company's internal tools to assemble page components, product shelves, and advertising AIGC.

Turning “suitable” into decisions people can inspect

I defined the workflow, data model, recommendation rules, interactions, and acceptance criteria. The team checked the business assumptions, and I used AI to help implement the frontend and backend. The central product work was making the selection criteria concrete:

  • Theme: which event provides the reason for this campaign?
  • Price and stock: does the available supply support the proposed offer?
  • Location and driving distance: is the product practical for someone attending the event? Proximity on a map alone does not settle that question.
  • Human review: what can the system recommend, and what should an operator adjust before handing the selection downstream?

Event heat is one input to this decision. A highly ranked event still needs appropriate supply and workable resource conditions. Keeping those judgments distinct makes it possible to inspect why a theme is attractive and why a particular product belongs with it.

Making review part of the workflow

Business-development teams need to propose and adjust selections; reviewers need to evaluate requests and allocate resources. I designed the request, review, and appeal steps around those responsibilities. The mechanism includes one submission per event, a partially visible success-rate estimate to guide requests, and a separate appeal path with reviewer scorecards.

These choices connect recommendation to action. Operators can consider the suggestions, change the selection, and move an agreed set of inputs toward the downstream system.

Focused AI modules and their evaluation

Event heat: AI-as-judge + BT ranking

The heat-quantification subtask uses AI-as-judge and a BT ranking model to support event comparison and ordering. Heat has no single clean target label, so the comparison criteria and the resulting order need review. I treat this as evidence for theme selection, alongside the product and resource constraints that determine the final recommendation.

Header images for event cards

I also built a two-stage workflow for event-card header images: a text model turns event information into a visual scene, an image model generates the background, and the frontend overlays the title. This separates readable typography from image generation. Images are generated in batches and read by the frontend. Advertising images and page assembly remain with the downstream team. Fixed samples for a recommendation subtask

For the LLM capability that suggests supporting materials for an event, I designed the prompt and evaluation method: seven prompt versions, compared on the same 103 real events. One failure linked a Mongolian artist's stadium concert to “grassland shuttle buses.” After restoring reasoning in the examples and adding negative examples, that targeted failure did not recur on the fixed regression set. This is evidence about that subtask and sample, rather than a measure of end-to-end advertising performance. Read the evaluation case →

Building with AI, checking the implementation

AI assisted the frontend and backend development. My responsibility was to translate the business rules into a consistent system and check that its behavior matched the intended decisions. Three implementation details made that work concrete:

  • One place to calculate a score. I proposed the success-rate calculation, the team validated it, and the backend became its authoritative source. Reference implementations and numeric comparison cases made the calculation checkable.
  • Explicit handoff semantics. Interface changes became integration checklists. Price units and submission snapshots were part of the contract, so a changed rule would not silently change the meaning of an earlier request.
  • Visible failures. A relationship field written as an empty array and the conversion Number(null) === 0 showed why missing data needs explicit handling. I worked through those failures and used checks to distinguish missing values from valid business values.

What feedback changed

During the on-site pilot, I worked with business-development users, collected feedback, and iterated on the frontend and backend with AI. That feedback changed the interface from a Gantt-style accordion to an event calendar with a persistent request area, made draft restoration explicit, and turned technical errors into messages operators could act on. Interviews with both business-development staff and merchants informed the product direction.

The contribution I want this case to show is the connection between business judgment and system delivery: defining a suitable theme and product set, making the decisions inspectable, and producing inputs another system can use. Broader impact needs to be assessed through selection quality, manual rework, and downstream usability; the subtask evaluation above does not establish campaign-level lift.

一场演唱会、赛事或节庆，可以成为一次活动的主题。要把主题变成可用的活动方案，还需要回答另一组问题： 哪些商品适合，价格和库存能否支持，用户从活动地点到商品所在地是否方便。 ResourceLoop 把这些判断组织成一套工作流，位于公司内部广告搭建系统的上游。

这套系统负责哪一段

ResourceLoop 筛选活动主题、召回和筛选商品供给，并让人能够查看、判断和调整推荐。 最终交给下游的是选定的主题、合适的商品供给和资源建议。 下游广告搭建 Agent 由其他团队负责，依托公司内部工具搭建页面组件、商品货架，并生成广告端需要的 AIGC 内容。

把“合适”拆成可以检查的选择依据

我负责定义工作流、数据模型、推荐规则、交互与验收标准。团队校验业务假设，我与 AI 协作完成前后端实现。 其中最核心的产品工作，是把选品与活动判断落实到具体条件：

  • 主题：这次活动围绕什么事件展开，为什么值得组织？
  • 价格与库存：现有供给能否支持活动准备提供的商品与优惠？
  • 地理位置与驾车距离：参加活动的人能否方便地到达商品所在地？地图上接近，还需要结合实际出行判断。
  • 人工审核：哪些内容由系统推荐，哪些需要运营在递交下游前调整？

事件热度是其中一个输入。热度较高的事件，仍然需要合适的商品和资源条件才能推进。 把这些判断分别保留下来，才能解释主题为什么值得考虑，以及某个商品为什么适合放进这次活动。

让人工判断有明确的位置

BD 需要提出并调整方案，审核员需要判断申请、分配资源。我围绕这些职责设计了申报、审核与申诉流程： 一个事件一次提交，适度展示成功率估计来帮助申报，并将申诉与审核分开，为审核员设置记分卡。

这些机制把推荐接到实际操作中。使用者能够考虑系统建议、修改选择，再把确认过的主题、商品与资源建议交给下游。

AI 子任务分别解决什么问题

事件热度：AI-as-judge + BT 排序

热度量化子任务使用 AI-as-judge 与 BT 排序模型，支持事件之间的比较与排序。 “热度”没有一个天然、干净的标签，因此比较依据和排序结果都需要检查。 它为主题选择提供参考，再结合商品与资源条件形成最终推荐。

事件卡片的头图生成

我还做了两阶段的头图生成：先由文本模型把事件信息转成画面场景，再交给图像模型生成背景，标题由前端叠加。 这样可以分别处理画面生成和文字可读性。图片批量生成后供前端读取。 广告端的图片生成和页面搭建由下游团队负责。 查看头图生成的实现细节 →

用固定样本检查推荐子能力

在“事件 → 配套物料”的 LLM 推荐子任务中，我负责 prompt 与评测方式：7 个 prompt 版本， 在同一批 103 条真实事件上逐版比较。一个具体错误是把“蒙古族艺人在体育馆开演唱会”关联到“草原接驳车”。 给示例补回推理路径、加入反面示例后，目标失败模式在这批固定回归样本中没有再次出现。 这个结果对应特定子任务与样本范围，不能直接用来衡量整套广告业务的效果。 查看评测案例 →

与 AI 协作实现，也把实现逐项检查清楚

AI 参与了前后端开发。我需要把业务规则转成一致的系统行为，并检查实现是否符合预期。 三个具体问题体现了这部分工作：

  • 分数在哪里计算。我提出成功率算法，团队校验后将后端作为统一计算来源， 用参考实现与数值对照样例检查结果。
  • 交接时字段代表什么。接口变更逐项整理成对接清单，价格单位和提交快照都纳入约定， 避免新规则悄悄改变历史申请的含义。
  • 错误怎样被发现。关联字段被写成空数组、Number(null) === 0 把缺失值变成零，都需要沿链路定位，并通过检查区分缺失数据和有效业务值。

反馈怎样改变了产品

驻场试点中，我面对 BD 收集反馈，与 AI 协作迭代前后端。反馈推动交互从甘特手风琴调整为事件日历与固定申报区， 补上明确的草稿回填，并把技术报错改成使用者知道怎样处理的信息。 面向 BD 与商家的双侧调研，也帮助我修正产品方向。

这个项目串起的是业务判断与系统交付：定义合适的主题和商品组合，让选择依据能够被检查， 再形成下游可以使用的输入。整体价值还需要结合选品质量、人工返工和下游可用性来衡量； 上面的子任务评测不能代替活动效果的验证。
